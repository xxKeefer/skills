## What you review

1. **What-not-why comments (Change Requested / Nit).** A comment that restates what the code plainly does adds noise and drifts out of sync. Remove it, or if the code needed explaining, the fix is clearer code (defer that to structure/naming: you just flag the comment).
   - `// loop over users` above a `users.map(...)`; `// set loading to true`; `// increment counter`.
2. **Commented-out code (Change Requested).** Never commit commented-out code: git has history. Remove it.
3. **Point-in-time comments that will drift stale (Change Requested / Nit).** Comments stating a fact true only *now*: references to specific line numbers, "currently…", "for now", "temporary", counts ("there are 17 namespaces"), "new" / "recently added", version numbers, or "see the function above/below". These rot. Remove or rewrite to a durable rationale.
4. **`TODO`/`FIXME` without a ticket, and ticket/AC refs on ordinary comments (Nit / Change Requested).** A bare TODO with no ticket reference is untracked debt. Flag it (link a ticket or remove). Conversely, flag **acceptance-criteria references** (`// (AC4)`, `// AC: …`) and **ticket numbers sprinkled on non-TODO comments**: ACs live in the test suite and the tracker, not the code; a ticket number is only legitimate inside a `TODO(<ticket>)`.
5. **Redundant JSDoc (Nit).** JSDoc is warranted only on **exported/public API** (lib entry points, shared composables/utilities consumed across modules). Flag JSDoc on internal/local functions, component-local helpers, or anything self-evident, and JSDoc that merely repeats the signature (`@param id the id`). A docblock that a rule asks for is not a finding: see "Comments that a rule asks for" in `SKILL.md`.
6. **Banner / section-divider noise (Nit).** `// ===== HELPERS =====`, decorative separators, `// end of function`: remove.
7. **Missing *why* on a genuine non-obvious hack (Nit: the one add-a-comment case).** If the diff introduces a non-obvious constraint (external quirk, deliberate not-the-obvious-thing, ordering dependency) with **no** explanatory comment, suggest a one-line *why*. Use sparingly: most code needs none.
8. **Comment/JSDoc already drifted from the code (Change Requested).** After a refactor, a comment or JSDoc that no longer matches the implementation: wrong `@param` names (or `@productType` instead of `@param productType`), a described return/behaviour the code changed, "resets all queries" when it now invalidates, a reference to a removed API (a removed dialog component after a migration). This is the single most common drift in review. Rewrite to match, or delete.
9. **Over-commenting / verbose comments (Change Requested when it exceeds the ceiling, else Nit).** Even a legitimate *why* is noise when it's bloated: prose that re-narrates the code line-by-line, the same rationale repeated on adjacent lines, or a comment on nearly every line of a block. Flag comment **density and length**, not just individual bad comments: a diff can be over-commented while each comment is defensible.

   **The ceiling: one line.** Two is a smell. Three or more is Change Requested unless the comment is carrying something a reader demonstrably cannot get anywhere else. The same applies to a doc block: when the JSDoc is longer than the function it documents, it is wrong. Judge every added comment against this before judging whether it is justified at all: a justified comment at four lines is still a finding. Apply the line count only when the repo's own comment rule sets a length limit. Without one, flag only re-narration, repetition, and density.
   Before you flag a header comment at the top of a new file, read [file-headers.md](file-headers.md).

   Rule of thumb: if consecutive statements each carry their own multi-line comment, most can go.

10. **The same fact stated through more than one channel (Change Requested).** A comment that repeats what a name, a type, a test title, an assertion message, a sibling JSDoc, or the literal on the next line already says. This is the highest-yield pattern in test files, where a fact routinely appears three times: in the `test('…')` title, in the message argument of the `expect(…)`, and again in a comment above it. The assertion message is the copy that survives (it is what a failing run prints), so cut the comment. Likewise a rationale pasted at N call sites belongs once, on the shared thing that exists because of it (the type, the helper, the constant), not at each caller. When the fact is app-specific, the single copy stays in the app that owns it. Never suggest moving app-specific rationale into a shared library, which would couple it to its consumers. Two apps stating their own copy of the same fact is not duplication.
18. **Comment prose style (Nit).** Hold added comments to Simplified Technical English (STE). Flag Latin abbreviations (`e.g.`, `i.e.`, `etc.`; write "such as", "in other words"), "execute" where "run" works, should/must hedging where the comment can state what happens, exclamation marks, rhetorical questions, a metaphor or idiom, a contraction, passive voice with a known actor ("the cache is cleared on logout" → "logout clears the cache"), two ideas in one sentence, or a missing subject ("Called on logout" → "The store calls this on logout"). Do not flag the codebase's own acronyms. Apply this rule only when the repo's own comment rule asks for a prose style.

20. **A comment that the diff makes untrue (Change Requested).** A changed line of code that contradicts a comment or docblock on an unchanged line near it. Examples: a comment that says "locale-less" above code that now pins a locale, or a docblock that names a step the code no longer runs. Anchor on the changed code line, and quote the stale comment in `detail`. Rewrite the comment to match, or delete it.
21. **A comment that lists the members of a growing set (Nit).** A comment or docblock that names each member of a set that the code will add to, such as each field a tool changes or each file in a folder. The list goes stale on the next addition. State the rule that the members share, or point at the code that holds the set.

When an added comment argues for the design or names code outside its own file, when the diff inserts a symbol below a doc block, or when the diff adds a lint suppression, read [reach-and-placement.md](reach-and-placement.md). It holds rules 11 to 14.

When an added comment gives a reason for code that the diff did not write, or carries a `NOTE:`, `TODO:`, or `FIXME:` marker, read [comment-style.md](comment-style.md). It holds rules 17 and 19.

Before calling a comment orphaned or dangling ("Likewise", "as above", "the same applies"), read the file around the hunk, not only the patch: the comment it leans on often sits on an unchanged line just outside the hunk.

## Out of lane (exception)

- **Exception: e2e page objects and setup helpers carry full JSDoc with `@param`/`@returns` by house convention**, and the repo's lint config may enforce it (`jsdoc/require-param` fails the build without them). Do not flag those **tags** as redundant restatement there. The exception covers the tags only: the **prose** in the same block is in lane and is held to the ceiling in rule 9, and a JSDoc claim that is *false* is always yours.

## Severity

- **Change Requested:** a comment that the diff makes untrue (20), a made-up reason for an existing pattern (17), commented-out code, comments/JSDoc already drifted from the code, a doc block detached from its declaration, AC references on comments, what-comments on non-trivial blocks that mislead, a comment of three or more lines that a shorter one would carry, a fact repeated across channels (comment + assertion message + test title), and a comment that reaches outside its own codebase (naming another repo, service, or file the reader cannot see from where it sits).
- **Nit:** a comment that lists the members of a growing set (21), a comment that only moves with its code, comment prose style (18), a marker on an unremarkable comment (19), redundant what-comments, redundant JSDoc, point-in-time phrasing, bare TODO, banner noise, a missing why on a subtle hack, a two-line comment that one line would carry, prose arguing the change to a reviewer.
- **Future:** documentation-debt sweeps beyond this diff.
